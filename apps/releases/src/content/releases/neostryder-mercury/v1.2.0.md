### Added

- [Visible] [Pipeline] **An unsubscribe skipped as unsafe now offers a semantic block rule next to the sender-domain blacklist entry.** The rule is one plain sentence describing the mail, such as marketing from one company on any sending domain, and it is stored with disposition 550. If the judge drafts nothing usable, or the rule fails the self-test against the flagged message, only the blacklist is offered. Both changes share one Approve/Discard card and apply only on approval. A benign FAILED offers nothing. The Unsubscribe button on Telegram briefs gets the same offer. An instruction that adds a fallback now proposes only the unsubscribe. Rebuild the backend container to pick this up.
- [Visible] [Pipeline] **Mercury can push accepted newsletters to Juhandu, a self-hosted feed reader, where they appear as reader items.** The push is off by default. To turn it on, rebuild the backend container and set `MERCURY_JUHANDU_PUSH`, `MERCURY_JUHANDU_URL`, and `MERCURY_JUHANDU_TOKEN`. Failed pushes are retried from an outbox file for up to 24 hours and never delay delivery.
- [Visible] [Dashboard] **The Review page can be filtered to one outcome.** Chips above the sample (All, Accepted, Deferred, Rejected) narrow both the sample and Recently reviewed to a single outcome, so you can work through one result at a time. The choice stays in the page address, so a reload or a shared link keeps it. Redeploy the Worker to pick this up. (#91)

- [Visible] [Dashboard] **You can change or undo a review label.** A misclick on the Review page is no longer final. Your 50 newest labels show under Recently reviewed, where you can pick a different answer or press Undo to put the message back in the sample. Redeploy the Worker to pick this up. (#89)

### Changed

- [Visible] [Extension] **The Unsubscribe quick-action now adds a fallback sentence asking for a semantic filter.** It fills in "Unsubscribe me from <sender domain>. If unsubscribe is unavailable find an appropriate semantic filter to block these safely." Nothing is blocked up front, because a rule is offered only after the unsubscribe proves unsafe and still needs approval. Install the next extension release to get it.

- [Visible] [Pipeline] **The browsing agent has a three-minute run budget.** The gateway's agent now runs at medium reasoning and gets a wrap-up notice at 144 seconds, so a saved unsubscribe is reported instead of re-checked. Update the gateway's launch command to pick this up.

- [Visible] [Dashboard] **Labeling a deferred (421) or rejected (550) message "Should be accepted" on the Review page delivers it to your inbox right away.** It goes through the same delivery as the Deliver + whitelist button on a Telegram report, minus the offer to whitelist the sender, and a note on the page says whether the message arrived. Every deferred message now keeps a sealed copy for seven days, whether or not it sent a Telegram report. A rejected message keeps no copy, so its note says nothing was delivered, and the label is saved anyway. Once a deferred message is delivered this way it also counts as accepted, so when the mail host retries it, the retry does not land in your inbox a second time. Redeploy the Worker and rebuild the backend to pick this up. (#89)

- [Visible] [Dashboard] **The Review page sample is sorted newest first.** Every message in the sample now sits in one list by the time it arrived, whatever its outcome, so it reads in the same order as Recently reviewed. Before, rejected messages came first, then accepted, then deferred, with no order inside each group. The messages are still chosen at random for each outcome. Redeploy the Worker to pick this up. (#89)

### Fixed

- [Visible] [Pipeline] **A brief IMAP connection hiccup at the mail host no longer fails delivery or sends a Telegram alert.** Mercury delivers accepted mail into the mailbox over IMAP, and ForwardEmail's IMAP server sometimes drops, refuses, or stalls a new connection, then answers normally seconds later. One such hiccup used to fail the delivery after a 45-second wait. Mercury then answered 421 and sent a Telegram alert about an accepted message it could not deliver, though the mail host's retry delivered the message minutes later. Delivery now makes up to three attempts at connecting, logging in, and checking for an existing copy of the message, with a short pause between attempts. MERCURY_IMAP_PREPARE_ATTEMPTS sets the attempt count (default 3) and MERCURY_IMAP_RETRY_PAUSE_SECONDS sets the pause (default 3). The append runs at most once per call, so a message cannot be stored twice, and a refused login is not retried. Deliveries now run one at a time, because a burst of mail opened several connections at once and the host refused some of them. A first failed delivery is only logged, and the Telegram alert goes out only when the mail host's retry also fails. Rebuild the backend container to pick this up.

- [Visible] [Pipeline] **Rule proposals now ask the agent gateway a second time after a timeout or gateway error.** A rule proposal (the instruction flagged in the Thunderbird extension) asks the agent gateway to interpret it. When the gateway timed out (504), could not be reached, or answered 502 or 503, the proposal failed and sent a "rule-proposal error" Telegram alert. That happened once when the machine running the gateway stalled for several minutes. A proposal now asks the gateway once more after one of those failures and reports an error only if the second ask also fails. Judging incoming mail still makes a single judge call, because it has to answer the mail host quickly. Rebuild the backend container to pick this up.

- [Visible] [Digest] **The insights paragraph in the daily digest now reports only what the stats show.** It no longer describes trends, causes, or maintenance advice, ranks counters against each other, or claims that one counter explains another. If every sentence is removed, the digest shows a plain summary built from the stats.
- [Visible] [Pipeline] **Accepted mail is no longer appended to the mailbox more than once.** The mail host's IMAP server sometimes aborts or times out an APPEND and still commits it, sometimes minutes later, so a retry stored a second copy, and one three-week scan found 12 Message-Ids with two to five copies. Delivery now searches the mailbox for the Message-Id before every APPEND, waits 5 minutes after a failed attempt before trying again, and gives IMAP connections a 45 second timeout (`MERCURY_IMAP_TIMEOUT_SECONDS`). Rebuild the backend container to pick this up. (#95)

- [Visible] [Pipeline] **A slow approved unsubscribe no longer shows up as a failed decision.** Mercury now hands the browsing task to the agent gateway as a background job and checks on it for up to 27 minutes. If the agent never reports back, Mercury treats the unsubscribe as done and says so; only an error or a failure the agent reports counts against it. The browsing prompt also tells the agent to stop at a page that says the change was saved. Rebuild the backend and redeploy the gateway to pick this up.

- [Visible] [Pipeline] **An approved unsubscribe from a sender that supports one-click unsubscribe is now sent by Mercury itself, and the browsing agent no longer takes a blank or off-topic page as the result.** On real Fandango mail, the agent opened the List-Unsubscribe link as an ordinary page and went wrong three ways: a JavaScript preference center that had not drawn yet came back FAILED although the opt-out was already recorded, the SMS sign-up page shown after the opt-out came back SKIPPED_UNSAFE, and the second listed route, a preference center with an "Unsubscribe from all" button, was never tried. When a message declares RFC 8058 one-click support and its HTTPS List-Unsubscribe link is on the sender's own domain, Mercury sends the one-click POST, and an accepted answer is recorded as UNSUBSCRIBED without starting the agent. If the POST is refused or fails, or the route is on another domain, the agent runs as before, and it now waits for a blank page to load, treats a preference center as a normal unsubscribe, skips a page that has nothing to do with unsubscribing, and tries every listed route before it reports FAILED. Rebuild the backend to pick this up. (#90)

- [Visible] [Pipeline] **Mail from an authenticated sender that matches a standing accept rule is delivered instead of held when the classifier calls it phishing.** Real Walmart order and delivery messages were held at 421 and paged Telegram as URGENT because the classifier read them as impersonation. The accept rule now wins when the judge names it by its exact text, the sender passed DMARC, the injection screen did not flag the message, and the classifier scores credential or payment requests and injection attempts below 0.70. If any of those fails, the message is still held. Redeploy the backend to pick this up. (#88)

- [Visible] [Digest] **The daily digest is delivered even when the mail it quotes contains a blocked hostname.** ForwardEmail rejected any digest with a hostname on Cloudflare Family DNS's block list, and the rejected digest was lost for the day. Hostnames in quoted mail and in the insights paragraph now appear as host[.]tld, and when a 554 reply still names a hostname, that hostname is defanged and the digest is sent again, for up to ten hostnames. Redeploy the backend to pick this up. (#87)
